# 规则说明

## 配置项

| 字段 | 含义 |
| --- | --- |
| 包名 | 精确匹配系统通知来源；应用名称不能替代包名 |
| 展示名称 | 自己定义的标签，后续候选记录保存此名称 |
| 支出关键词 / 句式 | 多项之间是“或”；普通关键词后紧随金额，也可用 `{金额}` 指定句式内的金额位置 |
| 排除词 | 任意一个出现在整段文本中就忽略该通知，优先于支出关键词 |
| 启用 | 保存为启用后才处理此 App 的新通知 |

一个包名对应一份配置，包含多条支出条件和排除词。编辑页逐条添加、修改或删除，不再按逗号或换行拆分；同一条中的逗号作为字面内容保留。每类最多 20 条，支出条件为 1～40 字符且不可留空；排除词可全部留空，空白行不参与匹配，已填写的单词最多 40 字符。旧配置中的列表逐项载入，存储格式不变。

## 配置导入与导出

入口为“设置 → 通知配置 → 配置导入与导出”。导出通过系统文件选择器保存 UTF-8 JSON，默认名为 `MoneyTrack-rules.json`；导入选择文件后先预览新增、覆盖、启用数量、每个应用的条件与排除词，以及主副联动，点击“确认导入”才写入。取消预览不会修改配置。

应用规则按包名合并：同包名的名称、全部匹配条件、排除词与启停状态整体替换；联动按主副包名组合合并，相同组合覆盖。文件未包含的配置保留。写入在 io 线程的单个 SQLite 事务中完成，任意一项失败全部回滚；主副来源须在现有或导入的识别规则中存在。导入会保留文件内的启用状态，预览中可核对；不会修改账单、标签、去重记录、持续监听开关或系统授权。新设备仍需用户到系统设置授权通知读取。

示例（全部为虚构配置）：

```json
{
  "format": "moneytrack-notification-rules",
  "version": 2,
  "rules": [
    {
      "packageName": "com.example.payment",
      "displayName": "虚构支付应用",
      "expenseKeywords": ["支出(消费{无关文字}){金额}元", "spent,done"],
      "excludedKeywords": [],
      "enabled": false
    }
  ],
  "links": []
}
```

文件格式版本独立于应用和数据库版本。本次应用仍为 0.2.2，数据库升级为 v8（迁移保留账单），文件格式为 v2；兼容没有 links 字段的 v1 规则文件，导入 v1 不修改现有联动。只接受支持的格式版本；字段类型必须正确，不能把布尔值写成字符串。每个包名和主副组合只能出现一次，每次最多 100 个应用、100 条联动、每类最多 20 条匹配条件、文件最大 128 KB；所有配置都沿用编辑页的业务校验，任意无效项将拒绝整个文件。空列表不删除现有配置。逗号、占位符和固定括号以原字符串保留；排除词可为 `[]`，空白排除项会忽略。

文件仅含用户定义的规则，不包含账单或通知原文。应用不申请存储或网络权限，仅通过用户选择的文件读取、保存配置。

## 主副通知联动

进入“设置 → 通知配置 → 主副通知联动”。先为两个应用配置识别规则，再选择主来源（如微信）、副来源（如银行卡），设置主通知前后各多少秒，主动启用并保存。默认前后各 30 秒，允许 1～300 秒。两端识别规则和联动均启用时才生效；一组主副组合只保存一条配置。同一来源可用于多个同角色组合，不能同时担任已启用联动的主、副角色，以免链式合并。

主、副通知仍先分别经过来源、启停、排除词与金额解析。只有金额分值完全相同、时间在指定范围内、仍待确认且只含一个通知身份的对方来源账单才能合并。按系统投递时间 sbn.postTime 比较，而非读取通知里的交易时间；在已经收到的候选中，先找主通知之前最近的副通知，再找之后最近的一条，距离相同按原账单 ID 排序。一条通知最多联动一次，不跨任意来源合并。银行卡先到、主来源先到以及投递处理顺序与时间戳不同的情况均可处理，无匹配时先保留独立待确认记录。

合并保留原账单 ID、金额、备注、标签和报销草稿，账单来源与归档时间使用主通知；今日、历史和详情显示“已联动：主来源 + 副来源”。不自动确认，仍须人工核对后计入支出。已确认、已移除、手工账单和升级前缺少来源包名的旧账单不参与联动；两端原有独立账单也不会因新增配置被追溯批量合并。

两条通知的摘要身份都写入 SQLite，服务重连、重复投递和进程重启不重复生成该账单。同来源连续同额消费不会彼此合并，每个组合最多容纳一主一副，之后的新通知仍需独立匹配。清空账本会同时清理这些身份，保留配置；删除联动只影响后续匹配，删除来源时同时移除相关联动配置，历史账单和身份仍保留。

文件中 links 的一项示例：

```json
{"mainPackageName":"com.example.wallet","secondaryPackageName":"com.example.bank","windowSeconds":30,"enabled":false}
```

此功能按用户指定的来源、金额与时间推断关联，无法证明是同一笔银行交易。多笔接近时间的同额主副通知可能配对不同，核对时应检查来源和金额；不承诺真实支付平台的通知格式或投递时序。

## 固定文字与无关文字

可添加：`支出(消费{无关文字}){金额}元`。

| 虚构通知 | 结果 |
| --- | --- |
| `支出(消费虚构商户)12.50元` | 1250 分：仅说明内容变化 |
| `支出(消费)12.50元` | 1250 分：说明为空 |
| `支出12.50元` | 不匹配：缺少固定的括号和消费文字 |
| `支出消费虚构商户12.50元` | 不匹配：缺少实际括号 |
| `支出(消费虚构)12元，另有20元` | 忽略：多个金额 |
| `支出(消费虚构)-12元` | 忽略：负数 |

`{金额}` 必须且只能出现一次，用于提取金额，前后有固定文字。`{无关文字}` 只能出现一次，位于金额前，匹配 0～128 个字符。括号和“消费”等其余字符全部按原文匹配，不再表示可选段；半角、全角括号也须与通知实际字符一致。括号没有分组语义，因此不要求配对或禁止嵌套。不支持直接写正则或无界 `.*`。

若通知没有括号，应单独配置 `支出消费{无关文字}{金额}元`；要识别 `支出12元`，可另加 `支出{金额}元`，不要省略固定文字。

扩展句式采用更保守的金额检查：说明不能吞掉负号、货币符号或不完整数字，通知出现其他金额时整条拒绝，包括无法确定用途的余额金额。若说明与金额边界不清晰，请加入固定文字帮助定位，而不要猜测金额。

排除词是选填项。删除所有排除行或清空输入均可；保存时空白行转为无排除词，测试和通知识别也不会把空字符串当成命中。已填写的排除词仍优先于匹配条件。

## 微信和支付宝默认配置

根据用户提供的通知格式，为以下精确包名提供可编辑预设；同时保留原有的通用支出关键词。

| 来源 | 包名 | 新增默认项 | 虚构测试文本 |
| --- | --- | --- | --- |
| 支付宝 | `com.eg.android.AlipayGphone` | `你有一笔{金额}元的支出`、`你有一笔{金额}元支出` | `你有一笔0.02元的支出，虚构测试` |
| 微信 | `com.tencent.mm` | `已支付` | `已支付8.80元，虚构商户` |

支付宝金额位于“支出”之前，因此使用句式而非只写“支出”，同时接受“元的支出”和“元支出”两种形式。句式必须且只能包含一个 `{金额}`，前后都要有文字；除 `{无关文字}` 占位符外，其余文字按字面匹配，不作为正则执行。例如缺少支出后缀的 `你有一笔12.50元，虚构说明` 不匹配这些句式。

新安装时两条规则默认关闭，测试后需由用户启用并保存。0.2.2 覆盖安装会为仍完整保留旧版默认关键词的微信、支付宝规则补上对应格式，也会为 0.2.1 的支付宝默认规则补上“元的支出”，保留名称、排除词及启停状态；自定义过的关键词不会被覆盖，删除过的规则不会重建。自定义规则可在编辑页点击“载入此应用默认支出关键词”，再测试并保存；此按钮只替换支出关键词，不改变排除词或启用选择。也可在原有词后单独追加 `你有一笔{金额}元的支出`，保留自己的其余关键词。

## 支持与不支持的文本

以下使用默认关键词，全部是虚构样本：

| 文本 | 结果 |
| --- | --- |
| 支付成功 ￥12.50 | 1250 分 |
| 消费：人民币1,234.56元 | 123456 分 |
| 支出0.1元 | 10 分 |
| 支付成功12元，余额800元 | 1200 分 |
| 你有一笔12.50元支出，虚构商户 | 支付宝预设：1250 分 |
| 你有一笔0.02元的支出，虚构测试 | 支付宝预设：2 分 |
| 已支付8.80元，虚构商户 | 微信预设：880 分 |
| 退款：支付成功12元 | 忽略：排除词 |
| 支出12元，支出20元 | 忽略：多笔金额 |
| 支出12 | 忽略：缺少人民币单位 |
| 支出12.345元 | 忽略：精度异常 |
| 向某商户支付了12元 | 默认不匹配，可把“支付了”加入关键词 |

普通关键词后的金额接受：可选空格/冒号 + 可选“人民币” + 可选人民币符号/CNY + 数字 + 可选小数 + 可选元/CNY。符号/CNY/元至少出现一种；句式也使用相同的金额校验，句式后缀已有的“元”可提供单位。不识别订单号、银行卡余额、其他币种或中文大写金额，不从无上下文数字猜测。

重叠关键词命中同一数字位置只算一次，例如“支付”和“已支付”同时匹配 `已支付12元`；不同位置的两笔同额支出仍属于多笔，不合并，也不猜测选哪一笔。

## 通知格式适配

服务优先读取展开正文 `EXTRA_BIG_TEXT`，否则普通正文 `EXTRA_TEXT`，最后尝试 `EXTRA_TEXT_LINES`，并与标题合并。它不累加多个正文版本，不读取聊天历史或自定义远程视图。标题和正文中重复出现同一笔完整金额时也可能被保守地视为多笔并忽略。

微信、支付宝预设依据用户提供的格式通过了虚构文本单元测试，尚未验证真实支付通知。实际通知因版本、地区、语言、交易类型、手机设置而异；用你实际可见通知的**脱敏文本**调整规则，不把真实通知提交到仓库。

如果启用规则后仍无记录，先验证测试区能否匹配，再检查来源包名、通知授权、服务连接状态，以及系统是否实际向监听器提供金额。App 没有发送的通知无法通过修改关键词补出来。

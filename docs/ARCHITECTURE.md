# 学习路线与架构

## 一条通知如何变成记录

```text
Android 系统
  → PaymentNotificationListener.onNotificationPosted
  → 按包名查启用规则；跳过分组摘要
  → 读取 title + 单个正文来源
  → ExpenseParser.parse
  → NotificationIdentity.fingerprint
  → LedgerDatabase.recordNotification（事务内身份去重、可选主副联动）
  → MainActivity 展示待确认
  → 用户确认 → 总额更新
```

监听接口和 Manifest 绑定方式来自 [Android 官方 NotificationListenerService 文档](https://developer.android.com/reference/android/service/notification/NotificationListenerService)。授权是系统的“通知使用权”，与 Android 13 的 `POST_NOTIFICATIONS`（向用户发通知）不同。普通监听不需要后者；只有用户主动开启“后台持续监听”时，才请求通知发送权限以显示监听状态和关闭入口。该权限不会增加读取能力。

## 为什么这样拆分

`core` 是普通 Kotlin/JVM 模块，输入是字符串和规则，输出是金额或 `null`。你可以先熟悉 `data class`、可空类型、集合、正则、单元测试，再学习 Android 生命周期。改解析逻辑不需要先在模拟器上重现支付。

`app` 处理 Android 专属工作。XML 定义 Material 3 控件，ViewBinding 生成类型安全的控件引用；Activity 只负责页面交互。界面采用 Material Components 1.13.0、AppCompatActivity 和 DayNight 主题，以资源提供浅色与深色配色；仍沿用 XML，不引入 Compose。版本要求参照 [Material 官方接入说明](https://github.com/material-components/material-components-android/blob/1.13.0/docs/getting-started.md) 和 [1.13.0 发布说明](https://github.com/material-components/material-components-android/releases/tag/1.13.0)，现有 JDK 17、Gradle 8.13、AGP 8.13.2、SDK 36 满足要求。SQLiteOpenHelper 明确展示建表、查询、绑定参数与唯一约束，之后可作为学习 Room 的对照。

一个 `Application` 共享数据库与串行 `Executor`。通知回调本身运行在主线程，数据库工作转移到后台线程；结果通过主线程 Handler 更新 UI。Activity 关闭后不再更新旧 View。进程被杀会结束线程，账本和规则仍保存在数据库，下次启动重新读取；没有后台永活保证。

## 金额与去重

金额以“分”的 Long 保存，例如 `12.50 元 → 1250`。BigDecimal 从字符串转换，避免浮点误差。排除负数、零、超过两位小数、超过一亿元的单笔金额。

`PaymentRulePresets` 按精确包名提供微信“已支付”和支付宝“你有一笔{金额}元的支出／元支出”预设。`ExpenseParser` 先检查排除词，再分别搜索每个普通关键词或句式；句式只允许一个 `{金额}`，前后文字经 `Regex.escape` 按字面处理，不执行用户正则。按数字起点合并重叠关键词的命中，防止同一金额被重复计数；不同位置的同额支出仍视为多笔而拒绝。各项独立搜索还可发现紧接在模板后缀“支出”后的另一笔，避免模板消费后缀时漏检。

指纹包含包名、系统通知 key、通知的 `when`（缺失时用投递时间）和金额。数据库 `UNIQUE` 约束处理重复回调，忽略或移除记录也保留指纹。v8 另有 notification_events 保存每条通知摘要到账单的映射；联动后两条身份均保留，账单仍只有一份。清空账本会连去重标记一起删除。

`core.NotificationLinkRule` 校验主副来源和窗口；`NotificationLinkMatcher` 只负责纯 Kotlin 的候选排序，不操作数据库。数据层在单个事务内检查摘要是否已经存在，然后选出相同分金额、待确认、只有一个身份的候选；交给 core 优先选择主通知前的副通知，其次向后，最后按距离和账单 ID 排序。默认前后各 30 秒，可配置 1～300 秒。系统投递时间用于联动窗口，通知 when 仅参与原有身份计算，两者用途不同。

两端识别规则和联动均需启用。匹配成功时追加第二条身份，并采用主来源名称及投递时间，保留原账单 ID、金额和附加信息；未命中则生成独立候选。单笔最多两个不同来源，已经联动、已确认、手工、已移除记录不参与，禁止已启用规则中的交叉主副角色，避免连锁合并。配置开启前已有的两笔记录不会主动追溯合并。同来源同额通知始终各自入库，重复回调依赖持久身份，而非直接丢弃同金额事件。

这不是支付订单号：发送方更换通知 ID 或时间时可能重复；若发送方复用了相同 ID、时间和金额，也可能漏掉一笔。此局限不能仅凭通知文本消除，因此保留人工确认。首版也不在连接时重放历史通知。

## 数据最小化

规则表存包名、展示名称、关键词、启用状态；notification_links 存主副包名、秒数和启用状态，notification_events 仅存摘要身份、账单外键、来源包名/自定义名称、系统投递时间和主副标记。账本表存来源名称、金额、记录时间、状态和唯一标识（通知摘要或手工 UUID），不存正文、标题、完整通知 key、商户或账号。金额确认只改变本机账本，不与支付 App 通信。

UI 上的移除属于逻辑删除：记录不再展示/统计，但仍在数据库中用于去重。真正删除全部记录使用“清空账本”。自动备份关闭，原始数据库未额外加密；配置可通过系统文档选择器主动导入导出，不包含账本，尚无账本导出/恢复。

## 推荐学习步骤

1. 读解析测试，新增“消费 ￥8.80”的用例，练习先写预期再改实现。
2. 在规则编辑页修改关键词，观察文字输入如何变成 `PaymentRule`。
3. 阅读 Manifest 和通知服务，理解系统绑定、权限和主线程。
4. 阅读数据库建表，理解主键、唯一约束、参数绑定与逻辑删除。
5. 学习 Activity 生命周期，试试旋转屏幕、后台返回和授权切换。
6. 阅读 `ManualExpense` 与手工记账页面，再逐步加入金额修正、分类与可复用列表。
7. 理解现有结构后再引入 Room、ViewModel、Flow 或 Compose，逐步替换并保持测试通过。

## 界面结构

`MainActivity` 使用 Material 底部导航和三个 XML 页面，避免为三个入口引入额外导航框架。今日页显示全部待确认和当天已确认记录；历史页按日、周、月查询已确认支出；设置页集中管理授权、后台模式、清空账本和通知配置入口。`NotificationConfigurationActivity` 再分别跳转识别规则、主副联动和导入导出，配置不挤在首页或设置页中。

`HistoryPeriod` 使用 `LocalDate` 和设备时区计算自然日、周一开始的周、自然月，再转换为时间戳。数据库使用 `[start, end)` 左闭右开条件，避免午夜重复统计；夏令时的一天不一定是 24 小时。通知按投递时间归档，联动时取主通知的投递时间，不因用户稍后确认而改变归属日期；手工记录按用户填写的支出时间归档。

`homeSnapshot` 分别读取待确认和当天已确认，避免历史记录挤掉待确认项。`historySnapshot` 的列表每次加载 100 条并允许加载更多，总额和数量由独立聚合查询覆盖整个区间，不随列表已加载条数变化。数据都在 `Application.io` 上读取，v1 → v2 的附加信息迁移不会删除旧账单。后续数据规模增长可使用 RecyclerView 复用卡片。

规则编辑页按应用信息、识别设置、测试预览分组，使用 Material 描边输入框、开关和确认对话框。根视图统一处理并消费系统栏边距，底部导航不再重复添加导航栏高度。

`BaseActivity` 共用 `FocusedInputScroller`：监听全局焦点、根布局和 IME inset 变化，在布局完成后计算最近 ScrollView 的实际可视区域，扣除自身系统栏/键盘 padding，并在输入框周围保留 16dp 空隙。普通字段连同 TextInputLayout 标签与提示一起露出，超长备注改为保证光标行可见；再次点击同一字段也重新检查位置。只在键盘可见时滚动，不替换控件已有的 onFocusChangeListener，因此报销失焦归一等业务仍由原控件处理；下拉菜单沿用自己的定位逻辑，页面销毁时移除监听与待执行回调。窗口仍保留 adjustResize；键盘边距依据见 [Android 官方输入法显示说明](https://developer.android.com/develop/ui/views/touch-and-input/keyboard-input/visibility)。

应用列表以 36dp 图标、名称/状态、包名组成约 76dp 高的横向卡片；选择应用与手动添加并列，配置步骤收进标题栏的说明按钮。条件编辑行使用编号、48dp 高的单行文本框和删除按钮，不占用浮动标签空间；超长文本在输入框内横向编辑，错误提示按需展开。动态行仍只通过规则数组恢复，避免重复 XML ID 串行。今日页的刷新按钮放在“今日账本”旁，继续调用原有刷新逻辑。

## 后台持续监听与重连

`NotificationConnection` 统一检查系统授权，调用公开的 `requestRebind`；请求有 2 秒节流，返回成功仅表示已提交，只有 `onListenerConnected` 才能显示“已连接”。断开后在 2、10、30 秒有限重试；连接成功或服务销毁时取消尚未执行的重试。回到应用前台也会在未连接时请求重连。没有授权时不会申请重连，也不会反复切换组件或修改安全设置。

用户从设置页主动开启后，独立的 `ContinuousListeningService` 以低重要性的持续通知展示连接状态和关闭入口，设置 `stopWithTask=false`。`PaymentNotificationListener` 始终只承担系统绑定与通知解析，不再混用 started/foreground 状态，避免主动启停与系统绑定生命周期互相干扰。

设置页把此模式与通知读取授权、连接状态放进同一个“通知识别”卡片，只显示一个后台状态按钮。按钮根据用户保存的开启选择或服务实际运行状态显示“开启后台识别 / 关闭后台识别”，启动仍经过原有系统权限检查；服务被中断但选择仍开启时，按钮仍可清除该选择，状态文字单独说明暂未运行。重新连接与后台设置并排显示，不再单独占用后台监听卡片。

`ListeningPreferences` 保存用户开启选择，`Application.backgroundListening` 表示进程内实际前台服务状态。被系统回收、断连或撤销授权不会被误显示成用户主动关闭；返回可见页面时，在已有权限满足后尝试恢复。只有设置页或持续通知的关闭操作才清除开启选择。普通系统绑定监听不依赖该前台服务。`START_STICKY` 仅允许系统按规则恢复，不保证强制停止或厂商清理后存活，也没有后台定时轮询或自动启动广播。

手动修复连接时，Android 14+ 通过公开的 `requestUnbind(component)` 和延迟的 `requestRebind(component)` 重置自有监听绑定；平时不会反复重置连接。授权设置优先打开该组件的详情页，不可用时回退到系统监听列表。未获读取授权时不申请绑定。

诊断只保存本次进程的最近接收时间和处理结果（未启用、未匹配、已去重、已生成候选、已联动），不保存通知标题、原文、账号或聊天。来自本应用的状态通知直接跳过，避免刷新状态时形成自通知循环。

新增 `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_SPECIAL_USE` 和 `POST_NOTIFICATIONS`；Android 14+ 为实际的持续通知处理声明 `specialUse` 及用途说明。只从用户可见页面启动，不从应用初始化或后台接收器偷偷启动。实现依据：[Android 前台服务启动约束](https://developer.android.com/develop/background-work/services/fgs/launch)、[specialUse 类型说明](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use)、[通知监听连接 API](https://developer.android.com/reference/android/service/notification/NotificationListenerService)。

持续模式只能改善存活，不能恢复已经漏掉的通知，也不绕过用户强制停止或厂商后台限制；实际机型仍需按测试指南验证。

## 手工记账

`今日 → ManualExpenseActivity → ManualExpense → LedgerDatabase.addManualExpense → publishChange → 今日/历史重新查询`。手工保存代表用户已经确认，不经过通知规则、不需要系统通知授权，数据库仍在 `MoneyTrackApplication.io` 操作。

`core.ManualExpense` 负责元到分的十进制格式校验、金额上限和记录模型校验。输入只接受数字及至多两位小数，拒绝零、负数、科学计数法、千分位和单位，不自动舍入。UI 只提示数字键盘而保留文本 KeyListener，防止粘贴时把非法字符静默删除后变成另一金额。

日期和时间使用 `WheelDateTimeDialog`：年、月、日、时、分均为 NumberPicker 滚轮，禁止子输入框接收键盘输入。切换年月时按该月天数缩短日范围，旋转后通过 DialogFragment 状态和 FragmentResult 恢复选择；横屏可滚动。所选本地日期和时间按设备时区合成时间戳；夏令时跳过的不存在时间会提示重新选择，回拨重叠时采用较早偏移。选中的本地时间和草稿 UUID 随页面状态恢复，输入框恢复金额与来源。

每个新表单产生独立 UUID，使用 `manual:UUID` 作为唯一标识，和通知 SHA-256 指纹分开；它标识一次提交，而不是按金额或时间合并交易。保存中禁用重复提交，数据库唯一索引在旋转、重试或进程恢复后仍能防止同一草稿重复入账。旋转后在同一个 io 队列核对草稿是否已经保存，且发布账本变更不依赖旧 Activity 的回调是否仍有效。单独打开的新表单可保存相同金额和相同时间的另一笔支出。

沿用现有 `expenses` 表：`status` 为 `confirmed`，`received_at` 对手工记录表示用户选择的支出时间，`source_name` 是手填来源或“手工记账”。读取时由指纹前缀得出 `Expense.manual` 并展示来源标记；旧通知记录仍按原规则显示。数据库 v2 通过追加字段和表的迁移保留手工记录的原身份，不进行数据重建。手工记录的逻辑移除仍保留唯一标识；清空账本才真正删除。

## 账单附加信息与 v2 迁移

`ExpenseMetadata` 包含用户输入的备注、独立的报销枚举、标签 ID 列表和累计已报销金额，统一校验 500 字符、8 个有效不重复标签的边界。确认状态仍保存在原 `status` 列；报销不自动确认，也不改变原金额。v5 起采用下文的净支出统计口径。

`onUpgrade` 对 v1 追加 `note`（默认空）与 `reimbursement`（默认 none），新建 `tags` 和 `expense_tags`；SQLiteOpenHelper 的升级事务保证失败回滚。启用外键；v6 起删除标签前先保留账单快照，再级联解除旧标签关联。真正删除账单时清理其关联与快照。原账单、时间、通知指纹、规则均不变，不删除或重建旧表。新建数据库也执行同一套追加逻辑。

`ExpenseDetailsActivity` 与 `ManualExpenseActivity` 共用 `ExpenseMetadataEditor`。手工新增的记录和附加信息在同一事务保存；同一草稿重试不覆盖第一次的备注/标签。详情保存附加信息时，备注与标签关系在同一事务更新；待确认详情的“记录支出”同时设置 confirmed。标签管理返回后刷新名称和可选集合，不覆盖尚未保存的文字；已保存到账单的删除标签从快照读取并保留选择；仅未保存、未关联的草稿标签随管理删除而移除。

列表按批量参数查询关联标签，避免每条账单单独查库；每批最多 500 个 ID，兼容加载更多时的 SQLite 参数限制。标签名称由用户管理，1～20 字符，名称唯一；更名通过稳定 ID 同步到所有关联账单。备注和标签不从通知原文中自动提取。

## 支付预设与 v3 迁移

v3 不改动账本和标签表。升级时仅查询微信、支付宝已存在的规则，当支出关键词列表与旧默认列表完全一致时更新该列；名称、排除词和启用状态保留。自定义关键词不覆盖，用户删除的规则不重新插入。直接从 v1 升级时，先执行 v2 附加信息迁移，再更新默认规则；整个 `onUpgrade` 由 SQLiteOpenHelper 事务保护。编辑页提供显式载入默认关键词的按钮，方便用户自行更新已自定义的规则。

v4 为支付宝增加“元的支出”句式。`updateLegacyDefaults` 同时识别最初的通用默认列表和 v3 的支付宝默认列表，只有完全相同时才升级；已有自定义项时由用户手动追加句式或载入默认。`onUpgrade` 对所有低于 v4 的数据库执行一次此更新，低于 v2 时仍先补齐附加信息表，不重建账本。


## 净支出与 v5 报销迁移

旧 `reimbursement` 列的 CHECK 只接受三个状态，v5 追加 `reimbursement_status`（四种状态）和 `reimbursed_amount_fen`（非负整数分），复制旧状态。旧列保留但不再读写，避免重建账本以及干扰原 ID、指纹、标签外键；新库执行相同追加步骤，v1～v4 都可依次升级。

`ExpenseMetadata.countedExpenseFen` 负责单笔口径：无报销、待报销计全额；已报销计零；部分报销计原金额减累计报销金额。部分报销金额必须大于零且小于原支出，元到分复用 core 的 BigDecimal 严格解析，不舍入。UI 失焦或提交时先调用 completeReimbursementIfCovered，将合法且达到/超过原支出的部分报销改为已报销、金额列归零；输入期间只预览零支出，不提前切状态。非法精度、零、负数和溢出不会通过自动转换。UI 保存前校验，数据库写入事务内再读取原金额校验，避免其他入口写入超额值；切换非部分报销状态时写入零，防止残留金额影响后续编辑。

`historySnapshot` 用相同口径的 SQL CASE 聚合整个筛选区间，列表、总额和笔数共同绑定报销状态条件；首页复用未筛选的查询。报销扣减归属原支出日期，不按收款日期生成收入；已报销保留记录和笔数，未确认或已移除始终不进入聚合。历史筛选与时间区间随页面状态恢复，修改账单后重新查询会让不再匹配的账单离开当前筛选结果。

报销表单显示数据库当前状态与“修改为”下拉菜单；候选状态、金额与原始输入随旋转恢复，当前状态始终来自数据库。详情页在 onCreate 中同步恢复草稿并独立保存 hasMetadataDraft，再异步加载账单；连续配置变更即使发生在查询完成前，也不能把已恢复的草稿当成空表单。部分报销展示金额输入和净支出预览。列表整张卡片按报销状态着色，待确认核对颜色优先，无报销不展示报销标记；原支出金额始终可见。历史筛选通过标题旁按钮打开圆角 PopupWindow，以状态色点、说明与对勾展示选项，不占独立整行；大字体时限制面板高度并允许滚动。标签管理每个标签一行，保留至少 48dp 的触摸高度。


## 标签快照与 v6 迁移

v6 只新建 `expense_tag_snapshots`，以 `(expense_id, original_tag_id)` 为主键，保留删除时的标签名。`expense_id` 外键跟随账单真正删除而清理，原标签 ID 不再关联 tags 表。删除标签时，在同一事务先把已有关联及名称写入快照，再删除可选标签；任一步失败整体回滚。tags 的 AUTOINCREMENT 保证重新创建同名标签也得到新 ID，旧账单快照不受新标签更名影响。

账单加载按每批最多 500 个 ID 分别查询当前标签与快照。`replaceTags` 区分该账单已存在的快照和可选标签：选中的快照原样保留，只有用户在账单内取消选择才删除快照；其他标签继续使用原外键关联。快照同样计入每单最多 8 个标签，不能把其他账单的快照 ID 附加到新账单。

`ExpenseMetadataEditor.showTags` 接收可选标签与该账单快照，在单行 ChipGroup 内合并展示，外层 HorizontalScrollView 提供横向滑动；右侧固定的“＋ 管理”按钮与标签保持同一行。管理页面返回时仅刷新可选集合与快照，保留未保存的备注、报销选择和金额。旧版已删除且未留快照的关联无法追溯。


## 标签顺序与 v7 迁移

v7 只给 tags 追加非负整数 sort_order。迁移按旧的名称顺序初始化位置，保留原标签 ID、账单关联和删除标签快照。所有标签查询按 sort_order、id 排列；新标签追加到末尾，更名不改位置，删除不影响其他标签的相对顺序。已删除快照仍排在可选标签之后。

TagManagerActivity 使用系统 DragEvent 在现有单行列表中排序，不增加依赖：按下拖动手柄即可拖放，靠近可视区上下边缘时自动滚动；取消拖放恢复原顺序，放下后在 Application.io 的事务中保存完整 ID 列表。事务重新核对标签集合，拒绝过时或重复的顺序，避免并发添加/删除时覆盖新数据；读屏提供上移/下移操作。

ReimbursementAppearance 统一报销卡片、当前状态文字与筛选色点的专用色，避免复用首页总额的主题绿和待确认黄色。报销表单单独覆盖主题强调色，其他页面保持原主题。


## 逐条条件编辑与扩展句式

RuleEditorActivity 通过 KeywordListEditor 管理支出/排除两组动态输入行，formRule 直接生成列表，不再 join/split 逗号。数据库 JSON 数组格式不变，不需要迁移，也不自动替换用户配置。每行错误复用 core 校验；支出空行保存时明确提示；排除词允许空白行，生成配置时忽略，全部空白可保存为 []。动态行复用 XML ID，禁止整个行从父视图恢复状态，由 Activity 的列表 Bundle 同步重建，避免旋转时相同 ID 让所有输入行串成相同文字。测试通知文本仍不保存到 Bundle。

ExpensePattern 只把 {无关文字} 编译为一个最长 128 字符的非贪婪说明段，其余文字整体转义；括号不再表示可选分组，旧金额模板和说明模板均按固定文字匹配。金额、币种和说明使用命名分组，不依赖捕获组序号。通知和规则内的中文逗号、冒号采用一致归一化。

扩展候选额外拒绝说明末尾的不完整数字、符号与通知中的其他金额；重叠普通条件不能绕过扩展检查。退款排除、来源精确匹配、启停、人民币格式、Long 分金额上限和通知指纹逻辑保持原约束。测试预览与通知服务仍调用同一个 ExpenseParser。


排除列表可为空，core 校验接受空白排除项但拒绝超长项；ExpenseParser 在 contains 前跳过空白项，防止空字符串匹配任意通知。UI 生成列表时先去掉空白排除行，保存与测试共用同一列表；不恢复默认排除词，不修改用户已有的非空排除词。
